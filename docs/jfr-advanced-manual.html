§ 01 / 13

心智模型：JFR 到底是什么

An always-on, in-process, event-based telemetry bus.

把 JFR 理解为内置在 JVM 里的、强类型的、带时间戳与栈的事件总线，而不是"一个 profiler"。它同时承载三类数据：持续时间事件（锁等待、IO、GC 停顿）、周期快照（CPU 负载、堆摘要、线程 CPU）与统计采样（执行栈采样、分配采样、存活对象采样）。

持续时间事件 Duration

有 startTime + duration，由 threshold 过滤：先测量，超过阈值才提交。典型：jdk.ThreadPark、jdk.SocketRead、jdk.GCPhasePause。

周期事件 Periodic

由 period 驱动，可取 1 s、everyChunk、beginChunk、endChunk。典型：jdk.CPULoad、jdk.ThreadCPULoad、jdk.ThreadDump。

采样事件 Sampled

由 period 或 throttle（如 150/s）控制速率。典型：jdk.ExecutionSample、jdk.ObjectAllocationSample、jdk.OldObjectSample。

专家注：为什么 JFR 能做到 <1%？四个设计决定：① 事件写入线程本地缓冲，热路径无锁；② 栈、线程、类、符号进入常量池去重，事件只存 ID；③ 整数采用 LEB128 变长压缩编码，时间戳用 TSC ticks；④ Java 事件类在加载时被插桩，未启用时 commit() 经 JIT 内联后接近死代码，事件对象经逃逸分析可被标量替换。开销真正的大头是栈采集，这也是调高 stackdepth 与降低阈值时开销上升的根源。

按 chunk 粒度淘汰只有当一个 chunk 的结束时间早于 maxage 窗口时，它才会被删除。因此实际保留的数据总是略多于 maxage；dump 的 maxage/begin 同样会带上整块 chunk，再由工具按时间截取。
不指定上限 = 250 MB启动时既未设 maxage 也未设 maxsize，JVM 会打印 No limit specified, using maxsize=250MB as default。高事件量的 profile 录制可能只覆盖几十分钟，务必显式设置。
多录制并存时的设置合并同一事件被多个 Recording 启用时，JVM 取最"详细"的设置：最低 threshold、最短 period、任一开启栈则开启栈。每个 Recording 拿到的数据可能多于它自身的配置；dump 时并不会按各自的阈值重新过滤。所以"临时开一个 profile 录制做诊断"会让常驻录制在这段时间里同样变重。
§ 04 / 13

采样原理与偏差

What the sampler sees, and what it silently misses.

jdk.ExecutionSample 不依赖 safepoint，因此没有经典的 safepoint bias。它有自己的偏差：采样器线程每个周期最多挑 5 个处于 Java 状态的线程、1 个处于 native 状态的线程，挂起线程后遍历栈。线程一多，覆盖率随之下降。JDK 25 的 JEP 509 CPU 时间采样按每个线程消耗的 CPU 时间触发，偏差模型完全不同。

运行 Java 代码（on-CPU） native 计算（on-CPU） native 阻塞 IO（off-CPU，但线程状态是 in_native） park / blocked Java 样本 native 样本 CPU 时间样本

ExecutionSample 的盲区

  • 线程数 ≫ 5 时，每个线程两次样本之间的间隔被拉长，短时热点可能完全漏采。
  • 样本数与 on-CPU 时间不成正比：只要线程处于 Java 状态就可能被选中，被 OS 抢占但未让出 Java 状态的线程同样计入。
  • NativeMethodSample 会把阻塞在 socket read 里的线程也算作 native 样本，这些线程实际 off-CPU，不能拿来做 CPU 归因。
  • GC、JIT 编译线程不是 Java 线程，不会出现在执行采样中，需要看 jdk.ThreadCPULoad 和 gc-cpu-time 视图。

CPUTimeSample（JEP 509，Linux，实验）

  • 基于每个线程的 CPU 时间定时器，线程每消耗固定量的 CPU 时间就触发一次采样，样本数与 CPU 消耗成正比。
  • 覆盖 Java 代码与 native 代码中的 CPU 消耗，off-CPU 等待天然不产生样本。
  • 通过 throttle 配置，可写速率（500/s）或 CPU 时间间隔（10ms）。
  • 丢样会以 jdk.CPUTimeSamplesLost 事件报告，分析时务必检查。

JDK 25 · JEP 518 协作式采样：栈到底在哪里被遍历

旧实现由采样线程挂起目标线程后异步遍历其栈，必须启发式地处理"栈处于不一致状态"的情况，稳定性风险高。JEP 518 改为把栈遍历交还给目标线程本身：

挂起并记录

采样线程挂起目标线程，只记录 PC / SP 等顶层帧信息，放入该线程的采样请求队列。

立即恢复

目标线程马上恢复执行，采样线程的工作量变得极小。

safepoint 处理

目标线程到达下一个 safepoint poll 时，在自身栈处于一致状态的前提下处理请求。

从记录位置重建

依据挂起时记录的顶层帧重建栈，样本位置仍是挂起时刻，不引入 safepoint bias。

分析工作流与火焰图

    
Triage in the terminal, deep-dive in a GUI, automate with JSON.

    
推荐三段式：终端分诊（jfr summary + jfr view，30 秒内判断方向），图形深挖（JMC / IntelliJ Profiler / async-profiler 转换器生成火焰图），脚本化回归（jfr print --json 或 RecordingFile API 生成指标，接入 CI）。

  


  

    
STEP 1 · 分诊
先看"有什么"
jfr summary 看事件分布：ExecutionSample 太少说明 CPU 不是主因；ThreadPark 暴增说明在等待；出现 jdk.DataLoss 说明缓冲不足。

    
STEP 2 · 定向
按假设选视图
hot-methods、gc-pauses、allocation-by-site、contention-by-site、latencies-by-type、pinned-threads。用 --verbose 查看视图背后的查询。

    
STEP 3 · 深挖
时间轴 + 栈聚合
JMC 的线程时间轴可以把 GC 停顿、锁等待、IO 叠在同一时刻对照；火焰图用于栈聚合，注意区分按方法与按行号两种聚合方式。

java · RecordingFile 统计分配热点


var bytesByClass = new HashMap<String, Long>();
try (var rf = new RecordingFile(Path.of("app.jfr"))) {
  while (rf.hasMoreEvents()) {
    RecordedEvent e = rf.readEvent();
    if (!e.getEventType().getName().equals("jdk.ObjectAllocationSample")) continue;
    // weight = 该样本代表的分配字节数（已按节流率放大）
    bytesByClass.merge(e.getClass("objectClass").getName(),
                       e.getLong("weight"), Long::sum);
  }
}

编程接口：自定义事件与事件流

    
Make your business semantics first-class citizens of the timeline.

    
自定义事件的最大价值是把业务语义（订单号、租户、traceId）钉在与 GC、锁、IO 相同的时间轴上。毛刺发生时，一眼就能看出那 200 ms 里 JVM 在干什么。

  


  

    
    
    
    
    
  

  

    

      
OrderEvent.java


@Name("com.acme.OrderPlaced")
@Label("Order Placed")
@Category({"Acme", "Trading"})
@Description("下单全链路耗时")
@StackTrace(false)          // 业务事件通常不需要栈，省下最大头的开销
@Threshold("5 ms")          // 默认阈值，可被 .jfc / 命令行覆盖
public class OrderEvent extends Event {
  @Label("Order Id")  public long orderId;
  @Label("Tenant")    public String tenant;
  @Label("Trace Id")  public String traceId;
  @DataAmount         public long payloadBytes;
}

// 热路径用法
var evt = new OrderEvent();
evt.begin();
Result r = engine.place(order);
evt.end();
if (evt.shouldCommit()) {          // 未启用或未超阈值时直接跳过字段赋值
  evt.orderId = order.id();
  evt.tenant = order.tenant();
  evt.traceId = MDC.get("traceId");
  evt.payloadBytes = r.size();
  evt.commit();
}

      
启用方式自定义事件默认启用、阈值取注解值。可以用 -XX:StartFlightRecording:com.acme.OrderPlaced#threshold=1ms 覆盖；若不在 .jfc 中，使用 jfr configure +com.acme.OrderPlaced#enabled=true 写入模板。

  e.commit();
});

      
回调要快周期回调在 JFR 内部线程中执行，不要做阻塞 IO；不再需要时用 FlightRecorder.removePeriodicEvent 注销，避免类卸载泄漏。

    

    

      
JfrWatchdog.java · 进程内实时告警


var rs = new RecordingStream();
rs.enable("jdk.CPULoad").withPeriod(Duration.ofSeconds(1));
rs.enable("jdk.GCPhasePause").withThreshold(Duration.ofMillis(50));
rs.enable("jdk.JavaMonitorEnter").withThreshold(Duration.ofMillis(10)).withStackTrace();
rs.setMaxAge(Duration.ofMinutes(5));    // 同时保留最近 5 分钟供事后 dump

rs.onEvent("jdk.CPULoad", e -> cpuGauge.set(e.getFloat("machineTotal")));
rs.onEvent("jdk.GCPhasePause", e ->
    log.warn("GC pause {} {} ms", e.getString("name"), e.getDuration().toMillis()));
rs.onEvent("jdk.JavaMonitorEnter", e ->
    contention.record(e.getClass("monitorClass").getName(), e.getDuration()));

rs.startAsync();
// 触发告警时把最近窗口落盘
// rs.dump(Path.of("/data/jfr/alert-" + System.currentTimeMillis() + ".jfr"));

      
延迟与顺序事件流依赖 JFR 约每秒一次的 flush，端到端延迟约 1–2 秒，不适合作为毫秒级熔断依据。高吞吐场景可 setReuse(true) 复用事件对象减少分配；若不关心顺序，setOrdered(false) 能进一步降低延迟。另一个进程可以用 EventStream.openRepository(path) 旁路消费同一个 repository。

    

    

      
RemoteTail.java · JDK 16+（模块 jdk.management.jfr）


var url = new JMXServiceURL("service:jmx:rmi:///jndi/rmi://10.0.3.17:7091/jmxrmi");
try (var connector = JMXConnectorFactory.connect(url);
     var rs = new RemoteRecordingStream(connector.getMBeanServerConnection())) {
  rs.enable("jdk.GCPhasePause");

JEP 520 · 无需改代码的方法级计时与追踪


# 追踪每一次调用（带栈），定位"谁在频繁触发 HashMap 扩容"
java '-XX:StartFlightRecording:jdk.MethodTrace#filter=java.util.HashMap::resize,filename=trace.jfr' -jar app.jar
jfr print --events jdk.MethodTrace --stack-depth 20 trace.jfr

# 统计调用次数与耗时：按类、方法或注解过滤
java '-XX:StartFlightRecording:jdk.MethodTiming#filter=com.acme.order.OrderService,filename=timing.jfr' -jar app.jar
jfr view method-timing timing.jfr

# 类初始化耗时排查
java '-XX:StartFlightRecording:jdk.MethodTiming#filter=::<clinit>,filename=clinit.jfr' -jar app.jar

      
何时用它替代采样采样回答"时间花在哪"，追踪回答"被调了多少次、每次多久、谁调的"。它通过字节码插桩实现，开销随 filter 范围线性增长，只对少量精确目标开启，切勿用宽泛的包名过滤。

基线：常驻录制方案

  
JAVA_TOOL_OPTIONS · 生产基线（JDK 21+）


# 先建好目录：dumppath 不存在时 JVM 会报 "Failure when starting JFR" 并拒绝启动
mkdir -p /data/jfr/repo /data/jfr/crash

-XX:StartFlightRecording:name=continuous,settings=default,disk=true,maxage=6h,maxsize=2g,dumponexit=true,filename=/data/jfr/exit-%p-%t.jfr
-XX:FlightRecorderOptions:repository=/data/jfr/repo,stackdepth=128,preserve-repository=true,dumppath=/data/jfr/crash

# Kubernetes preStop：优雅停机前先截取最近 30 分钟
jcmd 1 JFR.dump name=continuous begin=-30m filename=/data/jfr/prestop-%p-%t.jfr

# 告警联动：P99 告警触发时由 sidecar 执行
jcmd $(pgrep -f app.jar) JFR.dump name=continuous begin=-10m filename=/data/jfr/alert-%t.jfr


  

    
有界
maxage 与 maxsize 同时设置；repository 放在独立卷并监控磁盘。

    
可取证
preserve-repository 加 dumppath，进程崩溃后仍能拿到 chunk。

    
可触发
告警、发布、preStop 自动 dump，不依赖人工登录机器。

    
脱敏
外发前 jfr scrub，命令行参数和环境变量里常带密钥。
